# src/adapters/onboarding

## Scope

Agent-driven creation and repair of site adapters:

- `service.ts`: `OnboardingJobService`, the global FIFO queue with one running job; Add, Retry, Repair, Cancel, Remove; restart reconciliation; log streaming;
- `sdk-runner.ts`: `ClaudeAgentRunner` on the Claude Agent SDK;
- `helper-runtime.ts`: the helper runtime registry (`HelperRuntime`, `HelperRuntimes`): local probe, selection, `GET helper` status, the helper check, and the finish-tool round trip shared with `--sdk-check`;
- `claude-runtime.ts`: the Claude entry of that registry;
- `codex-runner.ts`: `CodexAgentRunner` on the Codex CLI (`codex app-server` over stdio), its launch configuration, the bridge's own Codex home, and the run guards; `codex-rpc.ts`: the JSON-RPC channel over the child's pipes; `codex-runtime.ts`: the Codex entry of the registry (probe, check); `codex-runtime.AGENTS-evidence.md`: the real-environment evidence of the Codex restrictions (Codex 0.160.0);
- `tools.ts`: the agent's in-process MCP tools;
- `agent-browser.ts`: the agent's browser sessions and scope;
- `files.ts`: staging file access and the read-only reference allowlist;
- `staging-validation.ts`: the service's own gate (full validation plus TypeScript check);
- `prompt.ts`: system, initial, and retry prompts;
- `job-store.ts`: persistence under `data/jobs/`;
- `types.ts`;
- `cli.ts` and `cli-args.ts`: `npm run site:onboard`.

Not in scope: the swap itself and removal (injected `promote`/`remove` from the registry operations), validation logic, the dashboard UI, git.

## Boundaries

- Imports `src/core`, `src/ports`, `src/adapters/aside` (hostname helpers), `registry`, `storage`, `validation`, and the page-script builder of `src/adapter-kit`; `cli.ts` also imports `src/app`. Never `mcp`, `oauth`, or `dashboard`.
- The agent may write only `manifest.json`, `adapter.ts`, `NOTES.md` inside `sites/<key>/.staging/`, and read only the reference allowlist: `docs/ADAPTERS.md`, `docs/BROWSER.md`, `sites/reuters/*` (the reference adapter), `src/adapter-kit/*.ts`, `src/ports/{adapter,manifest,browser}.ts`, `src/core/models.ts`, and for a repair the site's live files. Renaming those docs or their cited sections (ADAPTERS.md §10, §12) breaks the prompt and tools.

## Invariants

- The SDK session has `tools: []`, every built-in tool in `disallowedTools`, `permissionMode: "dontAsk"`, a PreToolUse hook denying non-bridge tools, `settingSources: []`, no skills, plugins, or other MCP servers, and is aborted if it still lists a built-in tool.
- The Codex session (`codex-runner.ts`; evidence in `codex-runtime.AGENTS-evidence.md`) runs `codex app-server --listen stdio:// --strict-config` with every feature that adds a tool disabled (shell, unified exec, code mode, multi-agent, hooks, apps, plugins, browser/computer use, image generation and viewing, goals, memories, skills search, …), `web_search="disabled"`, `tools.web_search=false`, `request_user_input` and `update_plan` off, `mcp_servers={}`, `project_doc_max_bytes=0`, `project_root_markers=[]`, skills off, approvals `never`, sandbox read-only, and a model catalog rewritten from `codex debug models` so no model asks for code mode, sub-agents, extra tools, shell, patches, or search. Its thread has `environments: []` (no execution environment: no shell, file, patch, image-view, or MCP-resource tool exists) and its `CODEX_HOME` an `environments.toml` with `include_local = false` (`thread/resume` takes no `environments` and would otherwise re-select the default `local` environment), the job's tools as `dynamicTools`, and the bridge's system prompt as `baseInstructions`. The run is refused if the thread reports an environment (a resumed thread that does is never used: the run returns `resumeFailed` before any turn, so the service starts a fresh session) or an instruction source, if any item other than a message, reasoning, compaction, or bridge tool call starts, if Codex asks for an approval, user input, or an elicitation, or if a configuration warning arrives; `--strict-config` makes an unknown restriction key a start failure. Its `CODEX_HOME` is the bridge's own (`data/codex-home/`, owner-only, empty `config.toml`, that `environments.toml`, `auth.json` linked to the user's sign-in, which the bridge never opens). The tool channel is the child's anonymous stdio pipes: no listener; a call must carry this run's thread id and one of this run's tools; the pipes close and the child is terminated when the run ends.
- Codex output is reduced to state and error kind before logging: stderr is classified (`config_rejected`, `not_signed_in`, `limit`, `network`, `other`), never logged; a usage limit fails the job with Codex's short limit text ("Codex usage limit reached: …").
- The agent's environment has no `BRIDGE_*` variables and no parent Claude Code session variables (`helperBaseEnv`, shared by both runtimes); for Claude `ANTHROPIC_API_KEY` is set only from the bridge config, else the local Claude Code login is used; for Codex every `CODEX_*`/`OPENAI_*` variable is dropped and `CODEX_HOME` is the bridge's own, so only the ChatGPT sign-in of this Mac is used.
- The agent's browser scope is the provisional hostnames, the live manifest's hosts (repair), and those staged `hostnames`/`extraAllowedHosts` that either share a registrable domain with a provisional host (auto-accepted, e.g. `dd.reuters.com` for `www.reuters.com`) or were approved by the user. A staged host outside those domains (e.g. `arcpublishing.com`) pauses the job as `awaiting_user` ("the adapter needs access to hosts outside <site>: …"); Retry approves the pending hosts (`approvedHosts` on the job record) and a later new foreign host pauses again. Full `run_validation` and `finish` are gated the same way. Hosts equal to, containing, or under another registered site's hostnames, IP literals, `localhost`, `.local`, and single-label names are never in scope.
- Agent scripts may not mention cookies, web storage (`localStorage`, `sessionStorage`, `indexedDB`, `cookieStore`), or read password values; they pass the same shim as adapter scripts; each step holds the site lock only for that step.
- `finish` is accepted only with a passed full validation whose hash matches the staged files and a clean type check; the service then validates again itself before promoting. The agent's claim is never trusted.
- Runtime selection: `auto` takes Claude when available, else Codex; `claude`/`codex` force one. "Available" is a local probe without a model call: installed and sign-in not known missing (`signedIn: null` counts). Each run records `runtime` on the job; a retry keeps the recorded runtime while it is available, else uses the configured one with a fresh session and a log summary (its `sessionId` is dropped). With nothing available the job fails with a message naming the sign-in. The registry decides what the build ships: Claude and Codex (`supported: ["claude", "codex"]`), both registered in `src/app/jobs.ts`, never special-cased in `service.ts`. If a Codex restriction below stops being enforceable on the installed Codex, ship Claude only: remove the Codex entry from `createHelperRuntimes` (back to `supported: ["claude"]`), never weaken a restriction.
- `helperStatus(lastCheck)` makes no model call; `helperCheck()` makes one round trip on `wouldUse` (none when nothing is available, `runtime: null`) and returns `{ at, runtime, ok, code, message }` with `code` in `ok | not_installed | not_signed_in | limit_reached | failed`. The service does not keep the last result; the caller stores it so it outlives a core restart.
- `lang` (`en` | `ko`, default and fallback `en`) is stored on the job by Add, Repair, and Retry (a Retry with `lang` replaces it, without keeps it); records without it read as `en`. The prompt tells the helper to write `requestedAction` in that language (the only language-dependent prompt line); the host-approval action the service writes exists in both languages (`HOST_APPROVAL_ACTIONS`) and follows the job's `lang`; reasons and logs stay English.
- One job runs at a time globally. Repair never changes the site's status; a failed Repair leaves the live adapter untouched; a failed or cancelled Add marks the site `failed`.
- Restart: running → failed "interrupted by restart; click Retry"; queued → requeued; `awaiting_user` → stays; `onboarding` sites without a queued or paused job → `failed`. Stop: running → failed "interrupted by shutdown; click Retry".
- Job logs hold narration and tool summaries (tool, URL without query, file name and size, status), never file contents, cookies, or keys.
- The CLI refuses to run while something answers on the public port (unless `--force`); exit codes 0 succeeded, 1 failed or cancelled, 2 setup, 3 awaiting the user.

## Patterns

- Retry resumes the same SDK session (`sessionId`); if resuming fails, a new session gets a summary of the earlier log and the staged files are kept.
- `report_blocked` must carry the smallest user action, phrased like "Log in to reuters.com in Aside (account u0), then click Retry".
- Default model `claude-opus-5-5` at `high` effort, 80 turns (`BRIDGE_ONBOARDING_MAX_TURNS`).
- Codex: `CODEX_BIN` (`config.executables.codex`) runs; the model is the Codex CLI's default unless `onboarding.codexModel` names one from its model list; the turn limit counts bridge tool calls. Retry resumes the same Codex thread (`thread/resume` in a new app-server process; the tools persist with the thread; no environment thanks to `environments.toml`); if that fails, or the resumed thread reports an environment, the service starts fresh with the log summary. The probe runs `CODEX_BIN --version` (installed) and `codex login status` against the user's Codex home (signed in: exit 0 → true, "Not logged in" → false, else null). The PATH of the Codex process gets the bridge's node folder first (the npm launcher is `#!/usr/bin/env node`).
- After a Codex upgrade, re-run the evidence of `codex-runtime.AGENTS-evidence.md` (capture of the model-visible tool list and the real refusal runs); a version other than the verified one logs a warning on every run.

## Tests

`helper-runtime.test.ts` covers selection, status and check shapes and codes with fake runtimes; `service-helper.test.ts` covers `lang` and `runtime` on jobs, old records, retry rules, and the host-approval text in both languages. `service.test.ts` drives the queue with a scripted agent runner (`test-fixtures.ts`): Add, name-based Add, blocked → Retry, failure paths for Add and Repair, cancel during a run, restart reconciliation. `tools.test.ts` covers write/read allowlists and script restrictions; `sdk-runner.test.ts` the session options and environment stripping; `codex-runner.test.ts` every restriction in the Codex launch arguments, thread parameters, model catalog, environment, and Codex home; `codex-process.test.ts` drives a fake `codex` process (`codex-test-fixtures.ts`): the channel's per-run checks and closure, the run guards, resume (including a resumed thread that reports an environment), limit and configuration errors, the probe, and the job service end to end on the Codex runtime; `staging-validation.test.ts` the hash and type-check gate. A real onboarding needs the user's site logins and the running Aside app.
