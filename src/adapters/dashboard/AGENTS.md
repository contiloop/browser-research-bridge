# src/adapters/dashboard

## Scope

The local admin surface: `server.ts` (`createAdminListener`: per-launch token, loopback bind, Hono app, static UI routes), `security.ts` (admin token file, Host/Origin guard, token-for-cookie exchange, cookie requirement for reads), `api.ts` (`/api` routes over the registry, job service, health checker, OAuth list/revoke, cache, browser status; SSE job log), `deps.ts` (`DashboardDeps`, the core's services; `DashboardSource`, what the process-lifetime page is built from: `logger`, `location`, `core()` → services or null, `runMode`, `settings`, `settingsPage` (`SettingsPageSupport`: `info()`, `preview(change)`, `supportedRuntimes()`, `revokeAllAppsOffline()`, composed in `src/app/settings-page.ts`; `src/app/bridge-process.ts` adds the `captchaAuto` part of the preview), `chatgpt` (the ChatGPT connection service), `helperChecks` (`HelperCheckLog`: `last()`, `run(jobs)`; the persisted last helper check, `src/app/helper-check.ts`), `copyPassphrase` (a function only: "Copy passphrase", returns `ok | not_set | locked | unavailable`, never the value)), and `ui/` (the settings page: plain `index.html`, `app.css`, and ES modules `app.js` (DOM and fetch), `i18n.js` (Korean/English wording), `labels.js` (labels of every closed value set), `instructions.js` (setup links, terminal commands, the Aside AI instruction texts: tunnel, connector, and the login text with its `loginTarget` check), `state.js` (pure page logic: Getting started and its "what to do next" line (`nextStep`), helper readiness, ChatGPT sub-steps, per-site guidance, when the login text is offered (`blockKind`, `offersLoginHelp`), passphrase generator, language choice); no build step and no external resources).

Not in scope: any public exposure, OAuth itself, job logic, health logic, cache storage; the dashboard only calls the services it is given.

## Boundaries

- Imports `src/adapters/oauth`, `onboarding`, `registry` (types and services) and `src/app` listener helpers (`startListener`, `requestLog`, `BridgeListener`, health result type, the run-mode controller type, the ChatGPT connection service type and its `validateSetupInput`) and the settings-store port type; never `aside` internals, `mcp`, or `sites/`.
- Must never be attached to the public listener or bound to anything but `127.0.0.1` (`assertLoopbackBind` throws otherwise).

## Invariants

- Each start generates a new 256-bit token, writes `data/admin-token` with mode 0600, prints the one-time link; stop deletes the file. In the bridge process the listener is started once per process (not per core start), so the token and cookie stay valid across core restarts.
- Routes resolve the core's services on every request (`core()`), never at construction. While the core is off (`setup`, `restarting`), the routes that need it (`overview`, `browser`, `sites…`, `jobs…`, `oauth…`, `cache…`, `helper…`, `chatgpt/retry`) answer 503 `{ error: "not_running", message }` after the guards; the UI files are still served. An SSE job stream stays bound to the core it opened on.
- `createAdminApp`/`createAdminListener` accept either a `DashboardSource` or plain `DashboardDeps` (bound to that one core; tests).
- Guard order on every request: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (else 403); `GET /?token=` with the right token sets `bridge_admin_<port>` (`HttpOnly; SameSite=Strict`) and redirects to `/`; reads without the cookie → 401; any method other than GET/HEAD/OPTIONS needs the cookie and an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>` (else 403).
- Responses carry a `'self'`-only CSP and `X-Frame-Options: DENY`; API bodies are limited to 64 KiB.
- No view exposes a token value or the passphrase; OAuth clients are shown by name, id, and token storage hashes.
- `OnboardingRequestError` codes map to HTTP: `invalid` → 400, `not_found` → 404, `conflict` → 409; unexpected errors → 500 with "see the bridge log".
- "Check now" runs only when the site is idle; a busy site returns `skipped` with the holder instead of waiting.
- Settings-page routes: `GET status`, `GET settings`, `GET chatgpt` answer in every mode; `PUT settings`, `POST restart`, `POST chatgpt/setup`, `DELETE chatgpt` are accepted in `setup` and `running` and answer 409 `busy` while the run-mode control is busy (`restarting`); `POST settings/passphrase/clipboard` answers in every mode, including `restarting` (it does not touch the core); `GET helper`, `POST helper/check`, `POST chatgpt/retry` are core routes (503 `not_running` when the core is off). Errors are `{ error, message }`, plus `fields` for input errors and `locked`.
- `GET settings` carries `captchaAuto` as a flat field (`true`, `false`, or `null` when the config file is unreadable or holds a non-boolean); `PUT settings` accepts `captchaAuto` (a boolean, else `invalid` with `fields.captchaAuto: "bad_value"`), written to `captcha.auto` through the store, and restarts the core like the other settings.
- `POST settings/passphrase/clipboard` ("Copy passphrase") calls `source.copyPassphrase()` and maps its result: `ok` → 200 `{ ok: true }`; `not_set` → 409 `not_set`; `locked` → 409 `locked` with `fields: { passphrase: "locked" }`; `unavailable` → 500 `unavailable`; absent → 404. It logs `passphrase copied to the clipboard` / `passphrase not copied to the clipboard` with the result code only. `not_set` and `unavailable` are in `API_ERROR_CODES`, which `ui.test.ts` holds equal to the page's labels.
- `PUT settings` order: body types (`bad_value`; a helper runtime outside `supportedRuntimes()` is `bad_value`; `captchaAuto` not a boolean is `bad_value`) → `preview` (`locked` 409 + fields, `invalid` 400 + fields with the store's codes, `file_unreadable` 409) → `busy` → no change (200 `{ changed: [], restarting: false, appsDisconnected: null }`) → inside `runMode.restart({ prepare })`: `job_running` (409; only a job in state `running`, unless `confirmInterrupt === true`) → `settings.write` (the store stays authoritative: its refusal or `changed: []` ends without a restart) → when `disconnectApps` is true and the passphrase changed: every OAuth client revoked through the running core's `oauth.revoke({ clientId })`, or `revokeAllAppsOffline()` when the core is off (`appsDisconnected` true; false when it failed, the passphrase stays changed; null when not asked) → 202 `{ changed, restarting: true, appsDisconnected }` as soon as the files are written, while the restart continues.
- `POST restart` and `DELETE chatgpt` check `busy` then `job_running`; `POST chatgpt/setup` checks the input (`validateSetupInput`) first, then `busy`, then `job_running`, then calls the service. ChatGPT service codes map to 400 `invalid`, 503 `not_running`, 500 `server_error` (`prepare_failed`, with its message), and 409 for every other code (`tool_missing`, `exists`, `busy`, `external`, `not_configured`, `file_unreadable`, `locked`, `config_invalid`). `chatgpt/retry` answers 202 when it started the tool again, 200 when nothing was done.
- The last helper check comes from `source.helperChecks` (persisted in `data/helper-check.json` by `src/app/helper-check.ts`, so `GET helper` reports it across core and process restarts, including the automatic check's result); `POST helper/check` runs through `helperChecks.run(jobs)`, which records and logs it and shares a check already in progress on the same core. Without `helperChecks` (a plain `DashboardDeps`, tests) the API keeps it in memory for the life of the page.
- `lang` on `POST sites`, `sites/:key/retry`, `sites/:key/repair`, `jobs/:id/retry` goes through `parseHelperLang` (missing or unknown → `en`); job summaries carry `lang` and `runtime` (`jobLang`, `jobRuntime`).
- The secrets a request may carry (the passphrase, the tunnel runtime key) are handed to the store or the ChatGPT service and never echoed, logged, or put into an error message; request bodies are never logged.
- The "not signed in" page shows Korean and English together and tells the user to double-click `Open Settings.command`.

- UI files are served only from the fixed `UI_FILES` list in `server.ts` (`UI_PATHS`); a new UI file is added to that list and to the static-file test, never by serving arbitrary paths.
- The page inserts server data as text only (no `innerHTML`), keeps secrets typed into fields out of browser storage and clears them once the program accepted them, remembers only the page language in `localStorage`, and generates passphrases with `crypto.getRandomValues`. Wording lives in `ui/i18n.js` and `ui/labels.js`; both languages must have the same keys and placeholders, and every closed value set (site status, job state and kind, outcome status, run mode, problem code, ChatGPT state, helper runtime, helper check code, API error and field codes) has a label in both. An unknown value is shown as received.
- The Aside instruction texts (`ui/instructions.js`) stop the AI before the runtime key is created and before the connector is submitted, forbid asking for, reading, or typing a key or passphrase and acting on the consent page, tell it not to open or operate the local settings page, and contain no secret and no settings-page address; only a well-formed tunnel id is filled in.
- The login text (offered on a `needs_login` site card and on a job paused with `blockKind: "login"`; a missing `blockKind` reads as `other`) asks the Aside AI to log in with the password already saved in the Aside browser, to stop and tell the user when none is saved or a code is asked for, never to ask for a password, and not to open the settings page. It names the site's `loginUrl`, else its first hostname, else the host of the job's address, and only a public web address or DNS name (no loopback, IP literal, `.local`, single-label name, port, or credentials); otherwise no text is offered.
- Page layout rules: Getting started is the home and starts with one "what to do next" sentence and its one action; every dictionary text has at most two sentences (`app.intro` one), and longer background is in keys ending in `.more`, shown only behind a "More" disclosure (`ui.test.ts` counts sentences); statuses are plain words on a coloured badge, raw values only under "Details"; one name per thing in each language. "Copy passphrase" (ChatGPT step f) calls `POST settings/passphrase/clipboard` and shows only the result; the page never receives the value. The captcha switch (`captchaAuto`) is under Settings with the note on where a text captcha's picture goes. Tunables are not on the page.

## Patterns

- UI files are read from disk on every request (next to this module, else `<repoRoot>/src/adapters/dashboard/ui/`), so UI edits need only a browser reload.
- The SSE job stream replays the log after `Last-Event-ID` (or `?after=`) and then forwards live events; keep event ids equal to log sequence numbers. The stream is bound to the core it opened on and ends when that core stops (checked on every event and at least once per ping interval); the page reconnects after a restart with the last id it showed.
- Only one Aside status probe runs at a time; concurrent `GET /api/browser` calls share it.

## Tests

`ui.test.ts` imports the plain UI modules: identical key and placeholder sets in both languages, the two-sentence rule, labels for every closed value set (compared with the server's sets, including `blockKind` and the clipboard codes), the instruction texts' stop sentences (including the login text) and the absence of secrets and settings-page addresses, the passphrase generator, Getting started, the "what to do next" line, helper readiness, sub-step states, per-site guidance, when the login text is offered, and a scan of `app.js` (no HTML insertion, only the language in `localStorage`, the clipboard route, no tunable). `dashboard.test.ts` covers the settings-page routes with fakes (every success shape and error code, the mode table, guard refusals of every new state-changing route without the cookie and with a foreign `Origin` (including `POST settings/passphrase/clipboard`), `disconnectApps`, `captchaAuto`, the clipboard route's four results, the kept and the persisted helper check, no secret in any body or log line, `lang` pass-through, the bilingual not-signed-in page); `src/app/settings-api.test.ts` drives them through the whole process with real files. It also covers the token exchange, Host/Origin/cookie guards (including a tunnel-like Host and a cross-origin POST), API routes, error mapping, SSE replay, and 503 `not_running` without a core plus picking up a replaced core; `src/app/run-mode.test.ts` covers the page across core restarts. Any new state-changing route must get a test proving it is refused without the cookie and with a foreign `Origin`.
