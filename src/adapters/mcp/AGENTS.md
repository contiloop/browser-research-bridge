# src/adapters/mcp

## Scope

The remote tool surface: `tools.ts` (`createBridgeMcpServer` with exactly `search`, `fetch`, `search_sites`, `read_documents`, `list_sites`, their descriptions, encodings, and `tool call` logging), `search-service.ts` (targets, concurrent per-site calls, merge, cursor, page chain, page cache, lifecycle feedback), `read-service.ts` (ref resolution, read gate, document cache, text budgets), `live-call.ts` (one adapter call in the site's shared pool (never exclusive) within the remaining budget; outcome defaults; `recordLiveOutcome`; `callWithChallenge`, the blocked → attempt → re-run flow), `challenge.ts` (`ChallengeCoordinator`: one quick captcha attempt in flight per site with the detection budget, the captcha-limited verdict, background attempts, `whenSettled`, abandonment, the budget arithmetic `planChallenge`/`canRerun`, the texts `captchaUnsolvedAction` and `captchaLimitedAction`), `assistant-tasks.ts` (`AssistantTaskCoordinator`: Aside AI tasks (`SiteAssistant`) for a site in the background — captcha and login triggers, one task per site, the pause and the `needs_user` hold, counting, the login confirmation hook, the probe, the per-site record for the settings page; the sentences `ASSISTANT_WORKING_ACTIONS` and `assistantAction(reason, account)`), `adapter-output.ts` (zod normalization of adapter responses), `list-sites.ts`, `http-handler.ts` (stateless Streamable HTTP), `deps.ts` (tool tunables and service dependencies).

Not in scope: authentication (the bearer middleware runs before the handler), adapter loading and lifecycle storage (registry), browser control (port), cache storage (storage), route registration (`src/app/public-server.ts`).

## Boundaries

- Imports `src/core`, `src/ports`, and the cache-key helpers of `src/adapters/storage`; never `aside`, `oauth`, `onboarding`, `dashboard`, or `sites/`. The Aside AI is reached only through the `SiteAssistant` port; the login confirmation (`HealthChecker.confirmLogin` in `src/app`) is injected as a function.
- No tool may accept a script, file path, or command, and no tool may reach a site that is not registered.

## Invariants

- `TOOL_NAMES` is exactly the five tools. `search`/`fetch` return `structuredContent` and the same JSON as text; the typed tools return text only.
- `SearchService.search` never throws; `ReadService.fetch`/`readDocuments` never throw; only the `fetch` tool returns `isError: true`.
- Every live outcome, including failures and `blocked`, is fed to `registry.recordOutcome` exactly once per site call. Only `rate_limited` starts the cool-down; `blocked` does not.
- Captcha attempts (`captcha.auto` on), per incident (nothing is remembered per site between calls): a blocked failure (`blocked: true` returned by the adapter or carried by a thrown `OutcomeError`, e.g. a page script's bot check; not `rate_limited`) gets one quick attempt per site and tool call. Inline only with at least `captchaDetectBudgetMs + captchaRerunReserveMs` of the call left, for `min(captchaAttemptBudgetMs, remaining − captchaRerunReserveMs)` (the slot wait included); otherwise the failure is returned at once with "The captcha could not be solved automatically. Open <url> in Aside, solve it, then retry" and an attempt runs in the background (one per site, coalesced). The port gets `detectBudgetMs = min(captchaDetectBudgetMs, its own budget)`, counted from the moment the slot is held. Then:
  - captcha-limited — the attempt did not act: `kind: "unknown"` with `rounds: 0` (nothing recognized, detection not finished in time) or `unavailable` (`available: false`, no `solveChallenge`): no re-run, no background attempt; the failure is returned at once as `access_denied`, `blocked`, with message and action "<site> is captcha-limited: its bot check cannot be solved automatically. Open <url> in Aside, solve it, then retry" (`captchaLimitedAction`; the search log carries "captcha-limited" instead of that message, which names the URL);
  - `kind: "none"`, a solvable kind (checkbox, slider, text, with or without a round), or an attempt that acted and still ended `unknown`: one re-run of the same adapter call while `captchaRerunReserveMs` is left (else the original failure); its outcome is recorded too. Re-run `ok`/`empty` → returned (the only confirmation; the solver never declares success); still blocked → the original failure with the could-not-be-solved action (naming the solver's message unless it said `solved`); any other re-run verdict as it is;
  - any other failure of the attempt (browser unavailable, refused by the scheduler, a joiner timing out, thrown) → the original failure with the could-not-be-solved action;
  - none of it starts a cool-down or changes the lifecycle status; setting off or no coordinator → today's behavior.
- The coordinator runs at most one attempt per site at a time (later callers join and wait at most their attempt budget, then act on the shared report for their own page), as a non-exclusive pool task (holder `captcha`) with the site's scope (hostnames ∪ extraAllowedHosts) on the read's URL, else the adapter session's last page, else `https://<first hostname>/`. A background attempt is abandoned when its site disappears from the registry (polled each second; the registry has no removal hook) or the core stops (`dispose`).
- `ChallengeGate.whenSettled(site)`: the report of the site's attempt in flight once the port's work has ended, or null at once when none runs; it joins and starts nothing.
- Aside AI tasks (`assistant-tasks.ts`, `assistant.auto` on and the CLI answered its probe; always in the background — the call never waits for the AI):
  - captcha: after a blocked failure (not `rate_limited`) every live call notes it (`noteBlocked`); while a task works on the site the call skips the own attempt and answers `access_denied`, blocked, with "The Aside AI is passing the check now; retry in a minute" (or the running task's sentence). A task starts — and the call answers `access_denied`, blocked, with that sentence (the captcha-limited message kept) — when `captcha.auto` is off, when the own attempt is captcha-limited, or when the own attempt went to the background (the task then waits for `whenSettled` and starts only when that report is captcha-limited, did not run, or there was none). When the own attempt acted, nothing starts: the next blocked call decides;
  - login: a live `auth_required` (after the lifecycle turned the site `needs_login`), a read of a `needs_login` site that answers `auth_required`, or a search naming a `needs_login` site with `site:` starts a login task; the entry or item carries "The Aside AI is logging in now; retry in a minute" (also while a task runs). An unnamed search only shows a running task's or the hold's sentence on the `needs_login` entry; it starts nothing;
  - one task per site (sites in parallel), a non-exclusive scheduler task with holder `assistant`, budget `assistantTaskBudgetMs`, only for a serving, loadable site that is not cooling down; the scheduler refusing it is not counted;
  - counting: `failed` counts; a captcha `done` followed by a blocked live call of the site within `assistantFailureWindowMs` counts; a login `done` calls `confirmLogin`, whose `auth_required` counts and whose busy/unreachable answer counts as neither. Two counted failures within the window pause the site's tasks for `assistantPauseMs` (calls keep today's actions). `needs_user` holds the site's tasks until "Check now" (`clearHold`) and calls answer with `assistantAction(reason, account)`. A task stopped at core stop never counts;
  - `done` alone never makes an outcome `ok`; the AI's text never reaches a log, a response, or `lastFailure`. One `assistant task` log line per finished task: site, purpose, verdict, reason, sessionId, durationMs, trigger;
  - `probe()` at core start and after a task failed for a CLI reason (`failed`/`other` without a session); a trigger never probes by itself (an unknown availability means no task; a probe still running is waited for). `dispose()` (core stop) aborts running tasks through their signal and waits a bounded time.
- Parallel tool calls and `read_documents`' concurrent reads on one site run in parallel up to the scheduler's per-site pool.
- Search pages are cached only when every searched site returned `ok` or `empty`; documents only when `ok`; cache errors are logged and treated as misses.
- The adapter's read verdict is never upgraded: a non-`ok` verdict drops any attached document, `ok` without a valid document becomes `adapter_error`.
- Budgets: whole call 90 s (`toolCallBudgetMs`) including lock waits; `fetch` text 60,000; `read_documents` 120,000 split evenly over `ok` documents with a 10,000 floor; document cap 100,000; excerpts 1,000.
- Each POST gets a fresh `McpServer`; GET/DELETE → 405; a client disconnect closes the server, which aborts tool handlers and, through their signal, browser tasks.
- `tool call` logs carry tool, client id, query clipped to 200 characters, statuses, counts, and duration, never result text. Captcha lines (`captcha attempt` from the port or, when the port was not reached, the coordinator; `captcha re-run`; `captcha-limited`; `captcha deferred to the background`) carry site, tool, kind, rounds, result, status, and duration, never a URL or page text.

## Patterns

- Tool descriptions are read by the research models; keep the qualifier syntax and the status list in them accurate when behavior changes.
- `INSTRUCTIONS` and the `search`/`fetch`/`search_sites`/`read_documents` descriptions state, in one fixed text for all sites, that the query is typed unchanged into each site's own search box (a few keywords), that results are login articles read only through `fetch`/`read_documents` and never by web browsing, that any URL on a registered site is readable, and that parallel calls are welcome; they do not point the model to its own web search. `tools.test.ts` pins these phrases, the five tool names, the ChatGPT output keys, and the ~900-character description limit.
- `settleEntry` turns an `ok` site that contributed nothing into `empty` with a specific message; keep that distinction when changing merge.

## Tests

`search-service.test.ts` and `read-service.test.ts` use stub registries and task runners (no browser); `makeMcpWorld({ challenge })` adds a coordinator over a fake port whose `solveChallenge` is scripted (or absent). `assistant-tasks.test.ts` covers the assistant task coordinator with the real scheduler and a scripted `FakeSiteAssistant` (`test/support/fake-site-assistant.ts`; the real Aside CLI never runs in tests): the task's fields and pool holder, the homepage fallback, one per site, setting off / unavailable / unprobed / cooling down / not serving, scheduler refusals not counted, waiting for the own attempt's report, the pause and its window, the hold and `clearHold`, captcha done-then-blocked counting, the CLI re-probe, the login confirmation (pass, `auth_required` counted, busy/unreachable neither), dispose, and the metadata-only log line; `makeMcpWorld({ assistant })` adds it to the service tests (read and search triggers). `challenge.test.ts` covers the coordinator with the real scheduler (pool task, scope, target page = the read's URL, else the session's last on-site page `pageUrl`, else the homepage; the detection budget passed to the port, clipped to its budget, and starting after the slot (fake timers); the captcha-limited verdict and the reports that re-run; coalescing, `join`, join timeout, background, dispose, removal, budget arithmetic, metadata-only logs). Cover: lifecycle entries for every non-active status, unknown `site:` values, no-terms queries, cursor round trips across pages and restarts, `page:N` chain walking, caching conditions, `blocked` feedback, read gates for each status, budget splitting, requested-id preservation, and the captcha flow (solved, unsolved, `kind: none`, captcha-limited (`unknown` with no round, unavailable, no solver: at once, no re-run, no background), acted-then-unknown, other attempt failures, setting off, inline vs background at the `captchaDetectBudgetMs + captchaRerunReserveMs` threshold, reserve, coalesced reads, one attempt per search call, throttle pages left alone).

- Aside AI triggers: a captcha task also starts when the bridge's own attempt did not run (`!report.ran`); a blocked failure keeps its own status, and a blocked `auth_required` starts a login task, not a captcha task.
