# src/app

## Scope

The composition root and process entry:

- `config.ts`: `loadConfig`, environment > `config/bridge.json` > defaults; passphrase check; `PUBLIC_URL` normalization; tunables; non-enumerable secrets; `loadConfigResult` (the same load, classified as `passphrase_missing` / `passphrase_too_short` / `config_invalid` instead of thrown); `resolveSettingsPageLocation` (admin port and data folder that never fail);
- `settings.ts`: `createSettingsStore`, the settings store (`src/adapters/settings`) over `.env` and `config/bridge.json` with the rules of `config.ts`;
- `app.ts`: `createApp`, the core factory, wires browser port, scheduler, cache, registry, validator, health checker, committer, OAuth server, search/read services, MCP handler, public app, and onboarding jobs into `bridge.services`; `start`/`stop`; console logger;
- `run-mode.ts`: `RunModeController`, the run modes `setup` / `running` / `restarting` with `problem` (`passphrase_missing`, `passphrase_too_short`, `config_invalid`, `start_failed`) and `restartedAt`; `start`, `restart({ reason?, prepare? })` (stop the core → `store.loadConfig()` → a new `createApp` → start), `stop`, `services()`, `current()`, hooks `onCoreStarted`/`onCoreStopping`; `RunModeBusyError` (`busy`), `RunModeStoppedError`;
- `chatgpt-connection.ts`: `ChatgptConnectionService`, the ChatGPT connection: `state()` (the six states, `managedBy`, `connectedApps`), `setup()`, `retry()`, `disconnect()`, and the run-mode hooks that run the connection tool with the core; `mcpTargetUrl`, `createConfigTargetResolver`, `validateSetupInput`, `DEFAULT_TUNNEL_RESOURCE_PREFIX`;
- `bridge-process.ts`: `startBridgeProcess` (settings-page location → settings page bound once → ChatGPT connection service and its hooks when a connection tool is given → core start attempt; `proc.chatgpt`; the page's `DashboardSource` carries the controller, the store, the settings-page support, and the ChatGPT service) and `processBanner`;
- `settings-page.ts`: `createSettingsPageSupport` (the dashboard's `SettingsPageSupport`): `info()` (read-only information from the current files; with a missing or short passphrase read again with a placeholder passphrase from `chatgptTargetFallback`, else null values), `preview(change)` (the store's checks in its order: `locked` → `invalid` codes → `file_unreadable`, then the fields that would change, compared with where the store writes; the `.env` passphrase is read only to compare), `supportedRuntimes()` (`SHIPPED_HELPER_RUNTIMES`), `revokeAllAppsOffline()` (deletes every client in the token file while the core is off);
- `public-server.ts`: the public Hono app (request log, CORS on `/mcp`, OAuth routes, bearer-protected `/mcp`, 404 for the rest) and `startListener`;
- `health.ts`: `HealthChecker`;
- `jobs.ts`: onboarding job service wiring, `BRIDGE_ONBOARDING_MAX_TURNS`, and `SHIPPED_HELPER_RUNTIMES` (what `createHelperRuntimes` registers; `jobs.test.ts` keeps the two equal);
- `main.ts`: builds the settings store, loads `src/adapter-kit` helpers, builds the one `TunnelClientConnectionTool` of the process (`binary` from `TUNNEL_CLIENT_BIN`), calls `startBridgeProcess`, prints the banner, handles SIGINT/SIGTERM.

Not in scope: business logic of any adapter; site specifics.

## Boundaries

- The only module allowed to instantiate concrete adapters and to import every adapter. `main.ts` is the only runtime importer of `src/adapter-kit` for the bridge process.
- Must not import `sites/` directly; adapters are loaded by the registry.

## Invariants

- `ConfigError.code` is `passphrase_missing`, `passphrase_too_short`, or `config_invalid`; `loadConfigResult` returns it with the message, so the validation rules exist only in `loadConfig`.
- `resolveSettingsPageLocation` takes each of `adminPort` and `dataDir` from a valid environment override, else a valid value in a readable config file, else the default (8788, `data`); a malformed file never makes it fail.
- New keys: `onboarding.runtime` (`auto` | `claude` | `codex`, default `auto`), `onboarding.codexModel` (string or null), `chatgpt` (`null`/absent, or `{ managed, tunnelId: tunnel_ + 32 hex, profile }`); environment `TUNNEL_CLIENT_BIN` and `CODEX_BIN` → `config.executables` (defaults `tunnel-client`, `codex`). All are in `config/bridge.example.json`, `.env.example`, and the known-key set.
- `loadConfig` throws `ConfigError` (in the process: `setup` mode, the core is not started, the settings page runs) when `BRIDGE_PASSPHRASE` is missing or shorter than 12 characters, when a port is not 1–65535, when a tunable is not a positive finite number, when `redirectUriAllowlist` or `oauth.extraResources` is malformed, or when `PUBLIC_URL` has a path, query, fragment, or credentials. Unknown keys only warn.
- Secrets live in `config.secrets`, defined non-enumerable, so serializing the config never prints them.
- Both listeners bind `127.0.0.1`; the public app serves only `/mcp` and the OAuth paths; request logs omit query strings and bodies.
- Process order: settings store (before anything changes `process.env`) → settings-page location (`store.pageLocation()`) → settings page bound on 127.0.0.1 (exit 1 only if it cannot bind) → core start attempt. The settings page and its token/cookie live for the whole process; the core is started, stopped, and restarted under it.
- Core start order: data dir (0700) → registry reconciliation → OAuth purge → onboarding restart reconciliation → public listener → daily purge timer and health timer → attached listeners (tests only) → background browser probe. Core stop order: health timer, purge timer, onboarding jobs, attached listeners (reverse), public listener, browser port. Process shutdown: core (through the controller), then the settings page. A second signal exits immediately with code 1; a graceful stop exits 0.
- Run modes: a configuration problem or a failed core start never ends the process; it leaves `setup` with `problem` set, the public port unbound, and nothing of the core running. `problem` is non-null exactly in `setup`. Every core start reads the files again through `store.loadConfig()` (never `loadConfig()` on `process.env`) and builds a new `createApp` instance; a stopped core is never reused. One start/restart at a time: a call during one rejects with `RunModeBusyError` (the API's 409 `busy`); the check is synchronous. A failed start stops whatever the half-started core had started. `onCoreStarted` hooks run after the mode is `running`, `onCoreStopping` hooks before the core stops; both are awaited and their errors only logged.
- A job running when the core stops fails under the existing rule (interrupted by shutdown; Retry continues it).
- The resource advertised to clients is `PUBLIC_URL + /mcp`; without `PUBLIC_URL` it is `http://localhost:<publicPort>/mcp` and the banner says only local clients can complete OAuth.
- ChatGPT connection: program-managed exactly when `config/bridge.json` has `chatgpt.managed: true` (`managedBy: "bridge"`); without it, an `oauth.extraResources` entry starting with the tunnel-service prefix is `external` and nothing of it is started, stopped, or changed (`retry`/`disconnect` refuse with `external`); neither is `not_configured`. Managed states: `stopped` whenever the core is off, else the tool's `starting`/`ready`/`failed` (`stopped` while the core runs only if the tool was stopped). `connectedApps` = OAuth clients with `activeTokens > 0`, null when the core is off.
- The managed tool starts only from the `onCoreStarted` hook (so never in `setup`, and only after a start with a valid passphrase), using the marker of the configuration the core started with; the `onCoreStopping` hook stops it before every core stop and at process shutdown. The profile targets `mcpTargetUrl(config)`: `<publicUrl>/mcp` when `publicUrl` is plain-http loopback on the public port (the default `http://localhost:<publicPort>`), else `http://127.0.0.1:<publicPort>/mcp`; never the settings-page port. In setup mode the target is read with a placeholder passphrase from the start environment (`chatgptTargetFallback`).
- `setup` order: validate (`invalid` + `fields`: `tunnelId` `empty`/`bad_format`, `runtimeKey` `empty`/`bad_format`, `profile` `bad_value`) → `busy` → `tool_missing` → `file_unreadable` (config file) → `config_invalid` (no target) → inside `restart({ prepare })`: tool `prepare` (`exists`, `prepare_failed` + `kind`) → one `store.write` (marker + add the address, remove a previous managed tunnel's address) → restart. A write failure removes the key/profile files this call created; a failure is answered after the exclusive section ended, with no restart. Success is answered as soon as the files are written (`{ ok: true, done }`; `done` follows the restart and never rejects). `disconnect`: tool stop → `removeKey` → write (marker `null`, address removed) → restart; the profile file is left.
- The runtime key is passed to `prepare` once and never stored, logged, or returned by the service.
- Health checks: first pass 60 s after start, then at most hourly; due sites checked one at a time; busy or cooling-down sites skipped.

## Patterns

- Tests build the app with `createApp` and fakes (browser port, agent runner, OAuth fetch) and bind port 0; process tests use `startBridgeProcess` with `adminPort: 0` and a `createCore` that injects a fake browser.
- New services are added to `BridgeServices` so the dashboard and CLIs get them through one object.
