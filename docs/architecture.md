# Architecture

## Topology

```
ChatGPT (developer-mode connector) ──► OpenAI Secure MCP Tunnel ◄── tunnel-client (outbound; a child of the bridge when program-managed)
                                                                         │
Claude (custom connector) ──► Cloudflare edge ◄── cloudflared (quick or named tunnel)
                                                                         │
                                                                         ▼
                              127.0.0.1:8787  public listener (Hono on @hono/node-server)
                              ├── /.well-known/oauth-*, /oauth/{register,authorize,token} ── OAuth server ── data/oauth/token-store.json
                              └── /mcp ── bearer check ── stateless MCP server (one McpServer per POST)
                                              │
                                     SearchService / ReadService ── result cache ── data/cache/
                                              │            └── challenge coordinator (blocked → one quick captcha attempt → re-run)
                                     site registry ── data/sites.json, sites/<key>/ (adapter modules)
                                              │
                                     scheduler (per-site pool of 3, exclusive tasks, 8-task cap, per-task politeness, cool-down)
                                              │
                                     sites/<key>/adapter.ts (search, read, smokeTest)
                                              │  ctx.browser (scoped to the site's hosts)
                                     Aside browser port ── page-script shim; captcha solver (solveChallenge)
                                              │  MCP over stdio, `repl` tool
                                     `aside mcp --account u0` child ── Aside app ── tabs with the user's logins ── the site

You ──► 127.0.0.1:8788  settings page (UI + /api), never tunneled; up for the whole process
            ├── settings store ── .env, config/bridge.json (set-only secrets, minimal-change edits)
            ├── run-mode control ── stops / starts / restarts the core (setup | running | restarting)
            ├── ChatGPT connection service ── tunnel-client: key file, profile, managed child (with the core)
            ├── helper checks ── data/helper-check.json (last check; automatic check 30 s after a core start)
            ├── Copy passphrase ── /usr/bin/pbcopy (the value from .env on stdin, never in a response)
            └── through the running core: registry, health checker, cache, OAuth client list/revoke,
                onboarding job service ── helper runtime (Claude Agent SDK → Anthropic, or Codex app-server → OpenAI)
                       │                  ── helper tools served by the bridge (in-process MCP / Codex dynamic tools over stdio)
                       ├── same browser port, scoped to the site being onboarded
                       ├── sites/<key>/.staging/ (manifest.json, adapter.ts, NOTES.md)
                       └── validation gate ── promotion (swap, hot reload) ── git commit of sites/<key>/
```

One Node process holds everything above the `aside mcp` child, in two layers:

- **The settings-page layer** (`src/app/bridge-process.ts`): the settings page, the settings store, run-mode control, the ChatGPT connection service, and the helper checks (`src/app/helper-check.ts`). Started once per process; the admin token and cookie live as long as it does.
- **The core** (`createApp` in `src/app/app.ts`): the public listener, OAuth, the MCP tools, the registry, search and read, onboarding jobs, health checks, and the browser port. Run-mode control builds a new core from the current files at every start and stops it on every restart. Without a valid passphrase, or after a configuration or start failure, there is no core (`setup` mode) and nothing listens on the public port.

The public and settings-page listeners are two ports of that process; both bind 127.0.0.1, and only the public port is ever a tunnel target. ChatGPT and Claude reach the same public port through different tunnels, at the same time if both run.

## Representative flow: `search` from ChatGPT

Query: `site:reuters inflation after:2026-09-01 limit:5`.

1. ChatGPT sends a JSON-RPC `tools/call` POST through the OpenAI tunnel; tunnel-client delivers it to `http://127.0.0.1:8787/mcp`.
2. The public listener logs the request (method, path, status, timing, client id), the bearer middleware hashes the access token and looks it up in the token store; an unknown, revoked, expired, or foreign-resource token ends here with 401.
3. The MCP handler builds a fresh MCP server for this request (stateless mode, JSON response, no session id) and dispatches `search`.
4. `SearchService` parses the query in the core (text `inflation`, sites `[reuters]`, after `2026-09-01`, limit 5), asks the registry for every registered site, and plans targets: `reuters` is `active` with the search capability, so it is the only target; with no `site:` qualifier every `active` site would be a target and every other registered site would get a status entry from its lifecycle status.
5. The search page cache is consulted with a key built from the normalized query, sites, date window, limit, and cursor; a hit returns at once.
6. On a miss, each target runs concurrently through `runAdapterTask`: the scheduler gives the call a place in the `reuters` pool (up to 3 calls of a site run side by side; an exclusive task such as a repair step or health check holds the site alone; when no place frees up in time, `timeout` names the holders), a browser session is opened scoped to `www.reuters.com` plus `dd.reuters.com` and `arcpublishing.com`, and the adapter's `search` runs with the native date window because Reuters declares `dateFilter`.
7. The Reuters adapter opens `https://www.reuters.com/site-search/?query=…` in a bridge tab and runs a page script, wrapped by the shim, that calls the site's own content API from inside the page; the script result returns through the `repl` tool as JSON.
8. The core validates the adapter response, builds result ids (`reuters:<Arc id>`), merges the sites' pages (dedup by normalized URL, newest first, cut to `limit`), records each site's resume point in an opaque cursor, stores the cursor in the page chain under `(query, page 2)`, and caches the page if every searched site returned `ok` or `empty`.
9. The live outcome is fed back to the registry (an `auth_required` would move the site to `needs_login`; a `rate_limited` would start a cool-down). A block or captcha page (`blocked: true`, returned by the adapter or thrown by the port when the site started a bot check during the page script) with `captcha.auto` on goes to the challenge coordinator first: one quick attempt by the port's solver as a pool task (holder `captcha`, detection bounded by `captchaDetectBudgetMs`) on the page the adapter's browser session last showed (for this search, the `site-search` page; the homepage when it showed none), then one re-run of the adapter call, whose outcome is recorded too. An attempt that could not act on the check (captcha-limited, such as DataDome's slider) answers at once without a re-run; without enough budget left, the attempt runs in the background and the failure is returned at once.
10. The tool returns `{ results, nextPage, siteStatuses }` as `structuredContent` and as the same JSON in a text block; the tool call is logged with client, clipped query, statuses, and duration.

`fetch` follows the same path from step 3 with `ReadService`: the ref is resolved to a site by id prefix or by URL hostname without network access, a cached `ok` document is served without the browser, otherwise the adapter's `read` opens the article, checks completeness, and the core truncates the text to the tool's budget. A blocked read's attempt targets the article's own URL.

## Settings flow (save on the settings page)

`PUT /api/settings` → guards (cookie, `Host`, `Origin`) → validation with the loader's rules (`settings-page.ts` `preview`) → `busy`/no-change/`job_running` checks → inside `RunModeController.restart({ prepare })`: the settings store writes `.env`/`config/bridge.json` → 202 to the page → the core-stopping hook stops a managed tunnel-client → the old core stops → `store.loadConfig()` re-reads the files → a new `createApp` core starts (or `setup` with the problem) → the core-started hook starts the managed tunnel-client. The page polls `GET /api/status` and keeps its cookie. ChatGPT setup and disconnect use the same restart path after the connection tool port has written or deleted its files.

## Onboarding flow (Add on the settings page)

`POST /api/sites` registers the site as `onboarding` under a provisional key and queues a job. The job service runs one job at a time on the helper runtime that `onboarding.runtime` selects (`auto`: Claude when available, else Codex): a Claude Agent SDK session (Opus 5.5, high effort, the local Claude Code login unless `ANTHROPIC_API_KEY` is set) or a `codex app-server` child on the local Codex sign-in, with no execution environment and the bridge's tools as its only tools. Either way the only tools are served by the bridge. The agent drives bridge tabs through the same browser port and shim, writes three files into `sites/<key>/.staging/`, and runs validation. When it calls `finish`, the service itself runs the full real-site validation and a TypeScript check of the staged folder, then promotes it: live files move to `.previous/`, staged files go live, the registry hot-reloads the module, the site becomes `active`, and git commits `sites/<key>/`.

## Update flow (opener)

Double-clicking `Open Settings.command` sources `ops/update-check.sh` before it opens the page: for a clone whose branch has an upstream and whose background service is registered for this folder (or not registered while nothing runs), it fetches the upstream (15 s limit), works out a state (`behind N`, `up_to_date`, `diverged`, `dirty`, `excluded`, `no_upstream`), asks the running settings page through the admin token's cookie exchange whether a helper job is `running`, and on the user's Enter runs `git pull --ff-only` → `npm ci` → `ops/install-launchd.sh --bridge`, which restarts the process on the new code. `<git dir>/brb-update-pending` marks an update whose `npm ci` or installer failed, and the next double-click finishes it. Details: `docs/operations.md` (Upgrade) and `ops/README.md`.

## Boundaries and what crosses them

| Boundary                                                    | Crosses                                                                                                                                                                            | Never crosses                                                                                       |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Tunnel → public listener                                    | MCP JSON-RPC over POST, OAuth discovery, registration, consent form, token requests                                                                                                | the dashboard, any file, any script, any route outside the public set                               |
| Bridge → research clients                                   | search results (titles, URLs, dates, excerpts up to 1,000 characters), article text, site list and statuses                                                                        | cookies, tokens, passphrase, page HTML, instructions added by the bridge                            |
| Bridge → `aside mcp`                                        | page-script strings after the static scan, wrapped in the shim                                                                                                                     | caller-supplied code; scripts that name the REPL's capability globals                               |
| Aside tabs → the web                                        | page loads, fetches, and navigations to the site's `hostnames ∪ extraAllowedHosts`; during a challenge attempt, also loads from the fixed captcha vendor hosts, on that tab only   | requests to undeclared hosts (blocked in the tab), the user's own tabs                              |
| Bridge → Aside's vision model (text captchas only)          | the cropped picture of the captcha, through Aside's `captcha.readText`                                                                                                             | the answer (typed inside the REPL call), page text, cookies                                         |
| Settings page → clipboard                                   | the stored passphrase, piped to `/usr/bin/pbcopy` on request                                                                                                                       | the value in a response, the page, a log, an argument, or an environment variable                   |
| Bridge → Anthropic (Claude helper) or OpenAI (Codex helper) | the helper's conversation: URL, user note, snapshots, screenshots, script output, written adapter code                                                                             | the passphrase, the runtime key, and other `BRIDGE_*` variables, cookies, files outside `.staging/` |
| Settings page → files                                       | the passphrase, helper runtime, Aside account, ChatGPT marker, accepted tunnel address (into `.env`/`config/bridge.json`); the runtime key (into its key file outside the project) | any secret back to the page, a log, or a commit                                                     |
| Bridge → tunnel-client                                      | the key file's location (`file:` reference), the profile name, the public side's `/mcp` address                                                                                    | the key itself, `BRIDGE_*` and OpenAI variables in its environment                                  |
| Bridge → git                                                | commits of exactly one `sites/<key>/` folder                                                                                                                                       | anything else; the bridge never pushes                                                              |
