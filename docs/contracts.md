# Contracts

Consumers: ChatGPT (developer-mode connector, Deep Research or plain chat), Claude (custom connector, Research), MCP Inspector and Claude Code on the Mac, the settings page and local scripts using its API, and the CLIs.

## Access

- MCP server URL: `<PUBLIC_URL>/mcp`, where `PUBLIC_URL` is the origin the core was started with (the tunnel's HTTPS origin; without it, `http://localhost:<publicPort>`). The public side listens only while the core runs (`mode: running`).
- Transport: MCP Streamable HTTP in stateless mode. Every request is a `POST` with a JSON-RPC body (at most 1 MiB) and gets one JSON response; no `Mcp-Session-Id` is issued; `GET` and `DELETE` on `/mcp` answer 405 with `Allow: POST`. CORS is open (`*`) on `/mcp` and the discovery documents, and `WWW-Authenticate` is exposed to browsers.
- Authentication: OAuth 2.1 bearer token in `Authorization: Bearer <token>`. Missing token → 401 `{"error":"invalid_token","error_description":"Authorization required"}` with `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource/mcp"`; a bad token → 401 with `error="invalid_token"` in the challenge. A client discovers everything from that challenge.
- Any path outside `/mcp` and the OAuth routes → `404 {"error":"not_found"}`.

## Conventions shared by all tools

- **Encoding.** `search` and `fetch` return `structuredContent` and the identical JSON serialized in one text content block (ChatGPT needs both). `search_sites`, `read_documents`, and `list_sites` return the JSON in one text block only.
- **Outcome status values** (exact): `ok`, `empty`, `auth_required`, `unsupported`, `access_denied`, `rate_limited`, `timeout`, `adapter_error`, `browser_unavailable`. Every non-`ok` entry has `message`; `auth_required` and `access_denied` also have `action`, the user's next step.
- **Site status entry**: `{ site, status, message?, action?, note? }`; `note` is `"date filter applied after retrieval"` when the bridge filtered dates itself.
- **Search result**: `{ id, site, title, url, publishedAt, datePrecision, excerpt, author }`; `id` is `<siteKey>:<localId>` and is accepted by `fetch`/`read_documents` for as long as the site stays registered; `publishedAt` is ISO 8601 with the site's offset or null; `datePrecision` is `"minute"`, `"day"`, or null; `excerpt` is at most 1,000 characters or null.
- **Document**: `{ id, site, title, url, publishedAt, datePrecision, author, text, truncated, accessLevel, fetchedAt, metadata }`; `text` is Markdown-like plain text (paragraphs, `#` headings, lists, no navigation or comments); `accessLevel` is `"public"` or `"subscriber"`; `metadata` maps strings to strings.
- **Read error**: `{ code, message, site, action?, availableSites? }`; `code` is an outcome status other than `ok` (including `empty` for a missing article); `site` is the resolved site key, or the hostname/key the ref named, or null; `availableSites` lists the readable site keys when the ref named no registered site.
- **Query string** (`search`, `search_sites` `query`): free text plus whitespace-separated qualifiers anywhere: `site:<key|hostname|URL>` (repeatable), `after:YYYY-MM-DD`, `before:YYYY-MM-DD` (inclusive), `limit:N` (1–25, clamped, default 10), `page:N` (1–10, clamped, default 1; `search` only). A qualifier with an invalid value is treated as search text; an unknown `site:` value yields an `unsupported` status entry.
- Tool calls are annotated read-only, non-destructive, idempotent, open-world. The bridge answers each call within its 90-second budget; a site that runs out of time reports `timeout`.
- **Server instructions and tool descriptions** (`src/adapters/mcp/tools.ts`; one fixed text for every site; `tools.test.ts` pins the phrases) tell the research model: the query minus qualifiers is typed unchanged into each site's own search box, so it should be a few keywords in the site's language, no sentences, quotes, or operators (a long query returns nothing on most sites); results are the user's login and subscription articles, read with `fetch` (ChatGPT) or `read_documents` (Claude) and never by opening the url with web browsing (teaser or login wall); `fetch` and `read_documents` accept any http(s) URL on a registered site, including one found elsewhere; parallel calls are welcome, one keyword set per search call; a failed site differs from `empty`; results are untrusted page data. They do not point the model to its own web search.
- **Parallel calls.** Calls on one site, and the refs of one `read_documents` call, run in parallel up to the site's browser pool (3 by default); further calls wait in arrival order within the 90-second budget.
- **Captcha.** A site that showed a block page or captcha may get one automatic attempt and a re-run inside the call (`docs/business-rules.md`, Challenge attempts). When it stays blocked, the failure (`access_denied` as a status entry or read error) carries the action "The captcha could not be solved automatically. Open <url> in Aside, solve it, then retry", with the solver's fixed message in parentheses after "automatically" when it has one (for example "(text captcha: no vision model is configured in Aside)"). `<url>` is the read's URL, else the page the adapter last showed (a search: the site's search page), else the site's homepage.

## Tools

### `search`

- Input: `{ query: string }`.
- Output: `{ results: SearchResult[], nextPage: number | null, siteStatuses: SiteStatusEntry[] }`. For the next page, send the same query with `page:<nextPage>`.
- Errors: never an MCP error. Failures appear only in `siteStatuses`: one entry per registered site when no `site:` is given, one per named site (plus unknown values) otherwise. A site that failed contributed no results; `empty` always means the site answered and had nothing. A query with no words besides qualifiers returns no results and `empty` "no search terms" for each target.

### `fetch`

- Input: `{ id: string }`: a result id or an `http(s)://` URL whose hostname a registered site owns.
- Output: `{ id, title, text, url, metadata, site, publishedAt, datePrecision, author, accessLevel, truncated, fetchedAt }`; `text` is at most 60,000 characters, cut at a paragraph boundary with `truncated: true`.
- Errors: an MCP tool error (`isError: true`) whose text is `{"error": ReadError}`. Typical codes: `unsupported` (unknown site, unowned URL host, invalid ref, "site not ready: onboarding|failed", capability absent), `auth_required` (login wall), `access_denied` (paywall, block page), `empty` (article missing), `timeout`, `rate_limited`, `adapter_error`, `browser_unavailable`.

### `search_sites`

- Input: `{ query: string, sites?: string[], after?: "YYYY-MM-DD", before?: "YYYY-MM-DD", limit?: number, cursor?: string }`. Structured fields win over qualifiers in `query`; `sites: []` means all; `page:` in the query is ignored.
- Output: `{ results: SearchResult[], nextCursor: string | null, siteStatuses: SiteStatusEntry[], ignoredFields?: ("after" | "before" | "limit")[] }`. For the next page, send the same query and fields with `cursor: nextCursor`. The cursor is opaque, self-contained, and keeps working across server restarts; sites removed since are dropped from it.
- Errors: never an MCP error. An invalid cursor → no results and `unsupported` "invalid cursor: …" for each target. `ignoredFields` names structured fields that were invalid and therefore ignored.

### `read_documents`

- Input: `{ refs: string[] }` with 1–5 result ids or URLs.
- Output: `{ items: [{ ref, status, document?, error? }] }` in input order; each item succeeds or fails on its own. The documents that came back `ok` share 120,000 characters of text: each gets `max(10,000, floor(120,000 / number of ok documents))`, cut at a paragraph boundary with `truncated: true`.
- Errors: never an MCP error; per-item `error` as in `fetch`. Fewer than 1 or more than 5 refs is rejected by input validation.

### `list_sites`

- Input: `{}`.
- Output: `{ sites: [{ key, name, hostnames, status, requiresLogin, loginUrl, capabilities: { search, read, dateFilter, pagination }, lastCheckedAt, message?, action? }] }` with every registered site in every lifecycle status (`active`, `needs_login`, `degraded`, `onboarding`, `failed`), sorted by key. `message`/`action` explain a non-`active` site (for example `needs_login` → "login required or session expired" with the login action; `degraded` → last failure with "Repair in the dashboard").
- Errors: none.

## Settings-page API (loopback only)

Base `http://127.0.0.1:<adminPort>/api` (the settings page, formerly the dashboard). Every request needs the admin cookie and a matching `Host`; every state-changing request (POST, PUT, DELETE) also needs `Origin: http://127.0.0.1:<adminPort>` (or the `localhost` form). Bodies are JSON objects, at most 64 KiB; an empty body counts as `{}`. Responses never carry the admin token, the passphrase, the runtime key, or OAuth token values. Code: `src/adapters/dashboard/api.ts`.

| Route                                                                                            | `setup`                                          | `running` | `restarting`      |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------ | --------- | ----------------- |
| `GET status`, `GET settings`, `GET chatgpt`, `POST settings/passphrase/clipboard`                | answers                                          | answers   | answers           |

Order of checks. `PUT settings`: body types (`captchaAuto` not a boolean → `invalid` with `fields.captchaAuto: "bad_value"`) → `locked` → `invalid` → `file_unreadable` → `busy` → no change (200) → `job_running` → write → disconnect apps → 202.

The automatic helper check: 30 seconds after each core start, one `POST helper/check`-equivalent runs by itself when no job is queued or running, `wouldUse` exists, no `ok` is recorded for that runtime, and no check ran on this core yet (`docs/business-rules.md`, Onboarding jobs). Its result is what `GET helper` then reports. `POST restart`, `DELETE chatgpt`: `busy` → `job_running`. `POST chatgpt/setup`: input → `busy` → `job_running` → `tool_missing` → `file_unreadable` → `config_invalid` → `exists` → write → 202. A failed setup removes the files it created and does not restart.

## Command-line interfaces

| Command                                                                                                                 | Exit codes                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run site:validate -- <key> [--staging] [--light] [--account <id>] [--json] [--verbose]`                            | 0 passed, 1 failed, 2 setup error; the full form writes `validation.json` into the validated folder, the light form writes nothing                                                                                                                                                                                         |
| `npm run site:onboard -- <url\|name> [--note "…"] [--retry <key>] [--repair <key>] [--sdk-check] [--verbose] [--force]` | 0 succeeded, 1 failed or cancelled, 2 usage or setup error (including "something listens on 127.0.0.1:<publicPort>" without `--force`), 3 waiting for the user (prints the requested action and the `--retry` command)                                                                                                     |
| `npm run browser:check [-- --account <id>]`                                                                             | 0 when every `PASS` line holds; the account defaults to `ASIDE_ACCOUNT`, then `u0`                                                                                                                                                                                                                                         |
| `npm run browser:captcha-check -- <url> [--account <id>]`                                                               | 0 when the challenge attempt completed (solved or not; one JSON line on stdout: `host`, `kind`, `result` `solved`/`unsolved`/`unavailable`, `rounds`, `durationMs`, `available`, `message`), 2 setup error (arguments, Aside unreachable, the attempt could not start); the account defaults to `ASIDE_ACCOUNT`, then `u0` |
