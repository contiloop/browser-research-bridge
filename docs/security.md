# Security

## Protected assets

| Asset                                                                                                                           | Where it lives                                                                                              | Threat it is protected against                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| The user's site logins (cookies, sessions)                                                                                      | the Aside browser profile                                                                                   | a remote caller using them for arbitrary sites or exfiltrating them                                                   |

## Exposure

The public listener binds `127.0.0.1:<publicPort>` (8787) and is reachable from outside only through the tunnels. It is bound only while the core runs, which needs a valid `BRIDGE_PASSPHRASE` (12 or more characters); in setup-only mode (the core is off because the passphrase is missing or too short, a settings file is invalid, or the start failed) nothing listens on the public port and no connection tool runs. It serves exactly:

| Route                                                                                   | Method                                              | Access                         |
| --------------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------------ |
| `/mcp`                                                                                  | POST (OPTIONS preflight; GET and DELETE answer 405) | Bearer access token            |
| `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` | GET                                                 | public                         |
| `/.well-known/oauth-authorization-server`                                               | GET                                                 | public                         |
| `/oauth/register`                                                                       | POST                                                | public; capped, body ≤ 64 KiB  |
| `/oauth/authorize`                                                                      | GET (consent page), POST (decision)                 | passphrase                     |
| `/oauth/token`                                                                          | POST, form-urlencoded only                          | PKCE verifier or refresh token |

Every other path answers `404 {"error":"not_found"}`, including `/` and `/api/*`. The settings page (admin listener) binds `127.0.0.1:<adminPort>` (8788) only, for the whole life of the process; its code refuses any other bind address, and tunnels must never point at it.

The bridge process opens no other port. Its child processes:

| Child                                                                      | Started when                                                                         | Channel                                                                                                                                                                                          | Exposure                                                                                                                   |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `aside mcp --account <id>`                                                 | first browser step                                                                   | stdio                                                                                                                                                                                            | none                                                                                                                       |
| `tunnel-client run` (the connection tool, program-managed connection only) | after each core start with a `chatgpt.managed` marker; stopped before each core stop | its own health listener on `127.0.0.1:0` (a free loopback port it writes to `<keyDir>/<profile>-health.url`); the bridge reads only `GET /readyz` there, and only from a loopback `http` address | outbound connection to OpenAI's tunnel service; its profile targets the public port's `/mcp`, never the settings-page port |
| `codex app-server --listen stdio://` (Codex helper runtime)                | one per helper run                                                                   | the child's anonymous stdio pipes; no listener; a tool call must carry this run's thread id and one of this run's tools                                                                          | closed and the child terminated when the run ends                                                                          |
| Claude Agent SDK process (Claude helper runtime)                           | one per helper run                                                                   | the SDK's in-process MCP server                                                                                                                                                                  | none                                                                                                                       |
| `git`                                                                      | auto-commit                                                                          | —                                                                                                                                                                                                | local only, never pushes                                                                                                   |

A connection made by hand (a tunnel address in `oauth.extraResources` without the managed marker) is `external`: the bridge never starts, stops, or changes it.

## Authentication flow (research clients)

1. **Discovery.** `/mcp` without a token → 401 with `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource/mcp"`. The protected-resource document names `resource = <PUBLIC_URL>/mcp` and the issuer `<PUBLIC_URL>`; the authorization-server document advertises PKCE `S256` only, response type `code`, grants `authorization_code` and `refresh_token`, and `client_id_metadata_document_supported: true`.
2. **Client identification**, one of:
   - **Dynamic Client Registration** (Claude, MCP Inspector, Claude Code). Failure paths: body not JSON or not an object → `invalid_client_metadata`; `redirect_uris` missing, empty, more than 10, longer than 2,048 characters, not absolute http(s), or carrying a fragment or credentials → `invalid_redirect_uri`; URIs outside the allowlist are silently dropped, and none left → `invalid_redirect_uri`; `grant_types` without `authorization_code` or with anything besides `refresh_token` → `invalid_client_metadata`; `response_types` other than `["code"]` → `invalid_client_metadata`; 50 stored DCR clients already → `invalid_client_metadata` "client registration limit reached". An omitted `token_endpoint_auth_method` registers a public client (`none`); `client_secret_post`/`client_secret_basic` get a secret that is stored only as a hash.
   - **Client ID Metadata Document** (ChatGPT): a `client_id` that starts with `https://` is fetched. Failure paths (`invalid_client`): URL without a path, with a fragment, credentials, dot segments, an IP literal, `localhost`, or a single-label host; fetch not answering 200 within 1.5 s, redirecting, or exceeding 16 KiB; not JSON; `client_id` inside not equal to the URL; a `client_secret` present; neither a preferred `token_endpoint_auth_method` of `none` (or omitted) nor `none` in `token_endpoint_auth_methods_supported`. ChatGPT's document prefers `private_key_jwt` but lists `none`; the bridge does not implement `private_key_jwt` and treats such a client as public. Accepted documents are cached in memory for 5 minutes. CIMD clients do not count toward the registration cap.
3. **Authorization request.** Before the redirect URI is trusted, every failure is a 400 page that does not redirect: missing or unknown `client_id`, `redirect_uri` not registered for the client (loopback URIs match on any port), `redirect_uri` omitted while the client has several, `redirect_uri` outside the configured allowlist, a repeated parameter. After it is trusted, failures redirect back with an error: `response_type` not `code` → `unsupported_response_type`; missing `code_challenge`, method not `S256`, or a challenge that is not 43 base64url characters → `invalid_request`; a `resource` that is neither `<PUBLIC_URL>/mcp` nor listed in `oauth.extraResources` → `invalid_target`.
4. **Consent.** The page shows the client name, client id, and redirect host and asks for the passphrase; its wording is in Korean and English together (fields, routes, and behavior are the same as before). "Deny" redirects with `access_denied`. A locked-out bucket → 429 page "Too many failed attempts". A wrong passphrase → 401 page and one failure counted. The right passphrase resets the bucket's failures and issues a single-use authorization code (stored hashed, valid 5 minutes) by redirect.
5. **Token exchange** (`POST /oauth/token`, form-urlencoded only, otherwise `invalid_request`). Client authentication: unknown client → 401 `invalid_client`; confidential client with a missing or wrong secret → 401 `invalid_client`; a Basic header and a body `client_id` that differ → `invalid_request`. Code grant: missing `code` or `code_verifier` → `invalid_request`; code unknown, used, or expired, issued to another client, `redirect_uri` different from the authorization request, or a verifier that fails S256 → `invalid_grant`; foreign `resource` → `invalid_target`. Success: an access token (1 hour) and a refresh token (30 days) of a new token family, both random 256-bit values stored only as sha256 hashes.
6. **Refresh.** Each refresh revokes the presented refresh token and issues a new pair in the same family. A refresh token that is unknown, belongs to another client, or has expired → `invalid_grant`. A rotated token presented again within 10 seconds → `invalid_grant` only (a client's own concurrent refresh); later than that → `invalid_grant` and the whole family is revoked (theft signal). A foreign `resource` → `invalid_target` without consuming the token.
7. **Resource access.** Each `/mcp` request's bearer token is hashed and looked up; unknown, revoked, expired, or bound to a resource the bridge no longer accepts → 401 `invalid_token`. Tokens are bound to the `resource` given at authorization, so changing `PUBLIC_URL` (and with it the resource) invalidates tokens bound to the old one.

### Consent lockout

- With `trustedProxyHeader` set (for example `CF-Connecting-IP` behind Cloudflare), failures count per client IP taken from the first value of that header: 5 failures within 15 minutes lock that IP for 15 minutes. Requests without the header share one bucket, `unknown`, with the same per-IP limit of 5.
- Without it, every request arrives from 127.0.0.1 through the tunnel, so one global bucket applies: 20 failures within 15 minutes lock consent for everyone for 15 minutes.
- Lockout state is in memory and resets when the bridge restarts. All thresholds are tunables (`consentFailuresPerIp`, `consentGlobalFailures`, `consentLockoutSeconds`).

### Redirect allowlist

Entries are exact URLs or trailing-`*` prefixes; loopback entries without a port match any port. Defaults: `https://claude.ai/api/mcp/auth_callback`, `https://chatgpt.com/connector_platform_oauth_redirect`, `https://chatgpt.com/connector/oauth/*` (ChatGPT's per-connector callback), `http://localhost/*`, `http://127.0.0.1/*`. A malformed entry, or `*` anywhere but the end, stops the bridge at startup.

## Authentication flow (settings page)

1. At every process start the settings page creates a random 256-bit admin token, writes it to `data/admin-token` (0600), and prints `http://127.0.0.1:<adminPort>/?token=<token>` in the banner. Core restarts (saving a setting, Restart, ChatGPT setup or disconnect) keep the token and cookie; only a new process issues a new one. A clean stop deletes the file. The opener (`Open Settings.command`) reads the file only to hand that link to `open` (the default browser) and never prints it.
2. Every request must carry `Host` equal to `127.0.0.1:<port>` or `localhost:<port>`; anything else → 403. This also defeats DNS rebinding and an accidental tunnel to the admin port.
3. `GET /?token=<token>` with the right token sets an `HttpOnly; SameSite=Strict` cookie `bridge_admin_<port>` and redirects to `/`; a wrong token → 401 page.
4. Reads (pages, assets, `GET /api/*`) without the cookie → 401.
5. State-changing requests (anything but GET, HEAD, OPTIONS: POST, PUT, DELETE) need the cookie and an `Origin` equal to `http://127.0.0.1:<port>` or `http://localhost:<port>`; missing or different → 403. A page loaded in the Aside browser therefore cannot drive the settings page even though it runs on the same Mac. This applies to every settings-page route (`PUT settings`, `POST restart`, `POST chatgpt/setup`, `POST chatgpt/retry`, `DELETE chatgpt`, `POST helper/check`), and each has a test refusing it without the cookie and with a foreign `Origin`.
6. After a process restart the old cookie and link stop working; the page shows a bilingual "not signed in" page that points to the opener. The new link is in the new banner and in `data/admin-token`.
7. The settings page opens in the default browser, which may be Aside; the owner chose this knowing that an AI operating Aside could then reach the page. Mitigations: the cookie and `Origin` checks above, the Aside instruction texts telling the AI not to open or operate the settings page, and the prohibitions of `INSTALL-WITH-AI.md`. A secret field (passphrase, runtime key) is never filled back in: the page never receives the value again after saving.

Runtime key leaked: revoke it on the OpenAI platform, then set up the connection again with a new key ("replace").

## Sensitive data policy

- **Site credentials** never pass through bridge code. Login state is inferred from page markers; the onboarding agent's scripts may not touch cookies, web storage, or password values; the cookie-bearing `fetch` drops `set-cookie` from responses.
- **Article text and search results** are sent to the research client's provider (OpenAI or Anthropic); this is accepted. The bridge adds no instructions to tool results and labels them as untrusted page data in the server instructions. Locally, documents are cached up to 24 hours and search pages 10 minutes in `data/cache/`.
- **Tunnel operators** (OpenAI for tunnel-client, Cloudflare for cloudflared) terminate TLS and see all public-listener traffic, including article text and the passphrase typed on the consent page.
- **The helper** sends the site URL, the user's note, page snapshots, screenshots, script output, and the generated adapter to the provider of its runtime: Anthropic for Claude, OpenAI for Codex. The settings page states which one receives page content for the runtime in use. The Claude SDK keeps session transcripts in `~/.claude/projects/`, Codex in `data/codex-home/sessions/` (both can contain page content). `BRIDGE_*` variables, a parent Claude Code session's variables, and for Codex every `CODEX_*`/`OPENAI_*` variable are removed from the helper's environment; for Codex, `CODEX_HOME` is the bridge's own folder, so no user configuration, instructions, plugins, or MCP servers are loaded. The Codex restrictions depend on experimental app-server features and were demonstrated on Codex 0.160.0; another version logs a warning on every run (`docs/tracking/findings.md`).
- **Secrets on the settings page** travel only from the browser to the page's own loopback origin, are written to their files, and are never returned: `GET settings` reports `set`/`valid`/`locked`, `GET chatgpt` reports `keyStored`. The page keeps typed secrets out of browser storage and clears the fields once accepted; it stores only the page language in `localStorage`.
- **Validation step d** fetches one gated page without cookies from the bridge process, following redirects only within the site's hosts.
- **Prompt injection**: page content read by the agent and article text returned to clients are data, never instructions; the agent's system prompt says so, its tools are the restricted set above, and every adapter passes the static check and real-site validation before it is loaded.
- **Files**: `data/` is 0700 and its files 0600; `.env` is always written 0600; `.env`, `config/bridge.json`, and `data/` are git-ignored; the runtime key file and tunnel credentials live outside the repository; the launchd log folder is 0700 because `bridge.out.log` holds each start's settings-page link.
- **Executables**: the program never downloads or installs an executable and never starts the Aside AI. The connection tool and Codex are found at `TUNNEL_CLIENT_BIN`/`CODEX_BIN` (set by the installer) or on `PATH`.
- **Git**: the bridge commits only `sites/<key>/` locally and never pushes; adapter folders contain code and notes, never credentials.
